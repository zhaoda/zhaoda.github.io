前天（10 月 13 日），Cognitum One 发布了开源 Agent 编排平台 Ruflo 的新版本。官方稿里一句话最抓人：**一个 Agent = 模型 + 脚手架（harness）**。模型负责想和写，脚手架负责给它工具、记忆、工作流、沙箱和控制，让它真的能干活。Ruflo 就是把 Claude Code、Codex 或任何 MCP 客户端，外面套一层"执行层"，把单个助手变成 100 多个专业智能体并行规划、编码、测试、做安全评审。

我不评价这个商业发布稿本身，我想聊的是它背后这个判断——**脚手架才是决定 Agent 能不能干工程活的那一半**。

顺带说一句时间线：Ruflo 这次发布落在 10 月上旬一波密集的"治理型"更新里——Copilot CLI 计算机使用预览、Claude Code Mods、MCP Toolbox Java SDK，各家不约而同地往"约束 Agent 能做什么、自动分担评审负担"的方向发力。风向很明显：行业已经从"Agent 能写多少代码"的炫技阶段，进入"Agent 怎么被管住、怎么被审计"的工程阶段。Ruflo 就是这波里的典型样本。<!--more-->

## 为什么是"脚手架"，不是"更强的模型"

这一年我做 Agent 工具越做越确信一件事：同样一个模型，裸奔和套上好脚手架，交付能力是两个物种。Ruflo 的新版本把这件事做到极致，两个核心能力都冲着"工程闭环"来：

1. **Ruflo Mods**：把一个"任务（mission）"展开成一条端到端流水线——调研、构建、测试、验证、安全、基准、学习。注意它的输入单位是"mission"不是"task"，一个 mission 下来，它自己拆活。
2. **统一控制平面（control plane）**：编排智能体小队、智能、安全、运维和网络扩展，关键地方保留人工确认。

技术细节官方也给了：queen-led 小队组织（蜂后式领导结构）、跨会话的持久共享记忆、按任务路由到合适的模型、记录每次运行的成本和成败。这是把"人管团队"那套搬进了机器里：有人分工、有人记账、有人拍板。

## 三个值得偷的工程设计

第一，**持久共享记忆**。单个 Agent 最大的毛病是失忆：一个会话里修好的坑，换个窗口重来又得踩一遍。Ruflo 让整个小队共享一块长期记忆。这是所有想把 Agent 用进真实项目的团队都该抄的作业——记忆层比 prompt 技巧重要一个数量级。

第二，**按任务路由模型**。不是所有活都值得上最贵的模型。调研用便宜模型、关键代码生成用强模型、测试判读用快模型。这对应工程管理里一个很朴素的道理：不要让资深工程师去贴发票。Agent 团队也一样，算力预算花在刀刃上，靠的不是省，而是分级。

第三，**记录"跑了什么、花了多少钱、过没过"**。这是最被低估的一点。很多团队引入 Agent 后第一笔糊涂账就是成本：到底替我省了多少人天、烧了多少 token，答不上来。Ruflo 把审计做成一等公民。我的判断是：**凡是上生产的 Agent 系统，成本可观测性和测试通过率，优先级都应该排在"更聪明的 prompt"前面**。

## 冷静一点：100 个 Agent 的代价

但我不打算把这个东西吹成银弹。100 个 Agent 并行，听着爽，坑也藏在里面：

- **协调成本会吃掉并行收益**。小队越大，queen 的调度开销越大，任务切分得不好就是一百个 Agent 在重复问同一个问题。分布式系统里"通信开销大于计算收益"的老教训，在 Agent 世界里会重演。
- **人工确认位是生死线**。官方说"关键地方保留人工确认"，这话是对的，但"关键地方"怎么定义是门手艺。放太宽，Agent 寸步难行；放太窄，一次删库操作就教你做人。
- **发布稿里的星数（7.4 万 star、1250 万 npm 下载）是热度指标，不是质量指标**。动手之前先看 issue 区和最近 commit，比看 star 靠谱。

这也是为什么我说它的价值在"判断"不在"工具"：你可以不用 Ruflo，但"Agent = 模型 + 脚手架"这个等式，你自己做 Agent 系统迟早会自己悟出来。不如现在就按这个等式设计。

## 给一线同学的实战清单

如果你正在给团队引入编码 Agent，不管用不用 Ruflo，按这个清单自查一遍：

1. **你的脚手架给 Agent 配了哪几样？** 工具调用、跨会话记忆、沙箱隔离、成本记账，缺哪样补哪样。别指望换个更强的模型解决脚手架的问题。
2. **任务拆分是"mission 级"还是"task 级"？** 只会接单步指令的 Agent 是高级补全；能把一个目标拆成调研-编码-测试-评审闭环的，才算工程助手。
3. **给 Agent 立规矩先于给它加能力**：安全红线（哪些操作必须人工确认）、成本上限（单任务 token 预算）、失败回滚策略。这三条写进配置里，而不是写进 prompt 里碰运气。
4. **先在一个小仓库试点，跑两周看三个数**：人工评审返工率、token 花费、真实交付周期。三个数都变好再推广。

## 结论

Ruflo 这次发布，与其说是"又一个 Agent 工具"，不如说给行业递了张答卷：**未来编码 Agent 的竞争，不在模型，在脚手架**。模型越来越强是确定的，但把模型变成能交付的工程团队，靠的是记忆、编排、路由、审计这些"脏活累活"。

昨天我说 AI 编程 Agent 的瓶颈在评审环节（见上一篇），今天补上下半句：**评审瓶颈的解法，一半在更好的评审工具，一半就在这样的脚手架设计里**——让 Agent 自己把测试、安全、记账先做一遍，人只审真正需要人判断的东西。
