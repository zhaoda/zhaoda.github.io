上周六，Together AI 发了一份安全公告，根因写得直白到有点难堪：开发公开仓库 xorl 的时候，**一只 AI 编程 Agent 把一把凭证 commit 进了公开仓库**。那把凭证能打开一个私有的 Hugging Face 仓库，里面存着从客户请求里采样的 Prompt。有人在提交被撤回之前拿到了凭证，把样本全下载走了。

这不是孤立事件。同一周，工业安全公司 Dragos 公布了一项从 7 月做到 11 月的诱饵实验：往各家 AI 服务里发了约 200 万条带唯一假密钥和假链接的 Prompt，然后坐等谁来用。结果是三家推理服务商被偷了数月，自己却全然不知。OpenRouter 随即下架了三家服务商，并把 125 个端点移出了"零数据留存"（Zero Data Retention，ZDR）的适用范围。

## Together AI：Agent 交的作业里夹着一把钥匙

先把 Together AI 这件事的链条捋清楚，因为它离我们写代码的人最近。

Together AI 做常规软件测试时，会从客户请求里采样一些 Prompt，存进一个私有的 Hugging Face 仓库。这些样本来自 2026 年 6 月 24 日、7 月 4 日、7 月 8 日、7 月 14 日前后发往 MiniMax M3、GLM-5.2、Kimi K2.6 这三个模型的请求。采样本身是经过授权的，仓库也是私有的。

问题出在开发流程上。在开发公司公开的 GitHub 仓库 xorl 时，一只 AI 编程 Agent 把一把能访问那个私有仓库的凭证 commit 了进去。Together AI 的自动扫描发现了泄露并撤回了提交，但窗口期已经够长：有人拿到了凭证，下载了全部样本。

偷走数据的人不止拿走就走。它在样本里搜索其他服务的凭证，并逐个验证是否有效。被验证的凭证里有 5 个是 Dragos 实验埋下的"金丝雀"（canary）——专门用来暴露非法访问的诱饵。这 5 个金丝雀的出现，等于给这起泄漏盖了个时间戳：被偷的 Prompt 确实落到了别人手里，而且有人在系统性地翻里面的密钥。

Together AI 事后的四条整改，我建议逐条看，因为每条都对应一个真实的失守点：

1. **用有作用域的、短期有效的凭证，能不用密钥就不用密钥**——长效高权限凭证一旦泄露，爆炸半径就是全部。
2. **检查所有 Pull Request 里的凭证**——不只是人提交的，Agent 提交的也要查。
3. **新账号默认开启零数据留存（ZDR）**——之前不是默认。
4. **更新 AI 编程 Agent 的使用流程**——第四条才是点名了真正的故障点：凭证不是人手滑贴进去的，是 Agent 在干活的过程中顺手交上去的。

公司还说正配合外部取证公司和执法部门调查，没有发现这起事件之外的更多 Prompt 泄漏，是否涉及个人敏感信息还在核查中，会直接联系受影响的客户。

## Dragos 的 200 万个诱饵：三种偷法，三种教训

Together AI 只是被 Dragos 的诱饵钓出来的冰山一角。Dragos 首席研究官 HD Moore 带队做的实验很简单，也很残酷：2026 年 7 月到 11 月之间，向广泛使用的 AI 服务发送约 200 万条 Prompt，每条带一个唯一的假密钥或唯一链接。一条假密钥只可能从一个地方被学到，所以只要有人用它，就证明有人读过那条 Prompt。

结果分三种偷法，每种都值得单独记一笔。

**第一种：直接攻破服务商。** 三家推理服务商被入侵，请求被复制了数月，最早的一家从 7 月中旬就开始了。其中规模最大的一起，攻击者针对数百个预埋的 AWS 密钥下手——每个密钥只发在一次请求里、只发给一家服务商，集中在 10 月下旬的几个短窗口。窗口内发出的请求**全部**被偷，连那些在模型运行前就被服务商拒绝的请求也被偷了。这说明攻击者是在请求到达的第一站就复制流量，而不是在推理栈深处动手。偷到手之后，攻击者在几小时内就开始试密钥、列 S3 存储桶、翻 Secrets Manager 和 Parameter Store，还试图创建 Bedrock API 密钥、添加 IAM 用户来固化访问权限，驱动了数万次 AWS API 调用。11 月 1 日，同一名攻击者还搬来了 ARTEX——一个 AI 驱动的渗透测试框架，只用来确认手里的密钥还活着。值得注意的是，同一名攻击者似乎用一台租来的服务器同时攻破了其中两家服务商。

**第二种：低价卖家顺手记日志。** 有些人在 AI 推理市场上以最低价挂出模型，打开请求日志，把流经的 Prompt 收集起来。做这事的人看起来像是个人用户，用家用宽带上网——其中一位在法国，用家里的 Mac 从两条 Prompt 里拿到密码后，亲手敲了 root SSH 登录尝试，同一台机器还测试了好几个预埋的 AWS 密钥。还有一家路由商悄悄把一部分流量转发到这个市场，客户完全不知情；另一家卖家则在每条 Prompt 里悄悄多加约 1000 个隐藏 token。

**第三种：模型方自己在"看"。** 一家没有点名的中国 AI 实验室，从 7 月到 10 月之间，取走了发往其模型的半数以上诱饵链接，其中约三分之二的请求明明标记了"不收集数据"或零数据留存。更麻烦的是，通过美国托管商转售该实验室模型的请求，流量同样回流到了这家实验室。还有一例：一条 Prompt 发出 24 天后，它的秘密链接被贴进了一个飞书群聊，两分钟内就有北京和上海的三台桌面电脑、三部手机打开了它。Dragos 只公开过这个链接的前 8 个字符，所以贴链接的人手里一定有一份缓存的完整 Prompt。

HD Moore 的总结只有一句话，但每个做 Agent 的人都该贴在墙上：**"A privacy flag doesn't help when the attacker is already inside."** 隐私开关约束不了已经进了门的人。

## OpenRouter 的反应：下架三家，125 个端点失去 ZDR 资格

OpenRouter 是把客户请求路由到一池第三方服务商的网关。11 月 22 日，它宣布下架三家服务商，125 个端点不再适用零数据留存，并通知了所有可能受影响的客户。同时它强调，OpenRouter 自身没有被攻破。

这里有个细节别忽略：Dragos 没有点名被攻破的三家是谁，OpenRouter 也没有点名下架的三家是谁，双方都没说这两组是不是同一批。已经公开表态的三家是 Phala、Together AI 和 Novita——但三家的性质完全不同：

- **Phala**：攻击者控制了一台推理服务器，能在请求处理过程中直接读取数据。事件在 11 月 8 日得到控制。经网关发往 Phala 的 DeepSeek V4 Flash 0731 模型的请求，在 10 月 21 日 00:00 UTC 到 11 月 8 日 05:35 UTC 之间的，都应视为已暴露，里面的密钥、token、密码都该轮换。
- **Novita**：路由配置问题导致部分 MiniMax 请求被转到了 MiniMax 官方 API，超出客户原本的预期。窗口是 2026 年 5 月 28 日到 11 月 11 日。
- **Together AI**：就是上面说的 Agent 提交凭证事件。

OpenRouter 还说，被移出 ZDR 资格的 125 个端点里，既有被研究点名的服务商，也有出于谨慎顺带切掉的；要恢复资格，得先拿出保证、通过验证。它还打算把研究者的诱饵测试方法常态化，持续检查，并核查网络路径，确认请求和响应有没有被转发给第三方。

## 你的 Prompt 到底经过了几手

这件事真正该改变的，是我们对"发一条 Prompt"这件事的默认假设。

我以前也默认：模型调用就是我和模型厂商之间的事，中间顶多隔一个网关。现在看，这个链条可以长得多：Agent 框架、网关、路由层、转售方、托管商、模型方，每一跳都可能留一份、转一手。ZDR 这类隐私开关只约束第一跳——你勾选了它，不代表第二跳、第三跳也认。Dragos 的实验里，标了 ZDR 的请求照样被取走，就是这个道理。

对我们写代码、搭 Agent 的人来说，有几件实事可以马上做：

**第一，别把真密钥放进 Prompt。** 任何时候都别。这是这周所有案例里最便宜的一课。Phala、Novita、Together AI 三家公告的共同结尾都是同一句话的变体：轮换你放进过请求里的密钥。Agent 会把能读到的东西都发出去，凭证也不例外——Moore 原话就是这么说的。

**第二，给 Agent 的仓库访问权设上限。** Together AI 的教训不是"别用 Agent 写代码"，而是 Agent 不该拿到能打开生产数据仓库的长效凭证。给 Agent 的凭证要短效、要限定作用域，能走无密钥（keyless）访问就别发密钥；Agent 的提交要过和人一样的密钥扫描——最好是提交前就拦，不是提交后撤回。

**第三，自己埋金丝雀。** Dragos 的方法完全可以缩小了自己用：在 Agent 和流水线日常发送的上下文里放一个假凭证（比如免费的 Thinkst Canarytoken），一旦有人用它，就当作一次安全事件来处理。诱饵便宜，被偷了才发现贵。

**第四，选路由要选上游，不要只选价格。** 走网关时，手动指定上游服务商，别用默认池；确认隐私设置真的改变了请求去向；远离转售市场——有些容量甚至跑在被偷的密钥上。实在要省心，要么直连一线厂商（一家公司、一份合同、一份隐私政策），要么自托管——后者是唯一保证没有第三方读你 Prompt 的办法。

## 同一个周末，另一边的教训也一样

有意思的是，就在 Together AI 发公告的同一天，OpenAI 也挂了 211 分钟。11 月 21 日下午 1:48 到 5:21（太平洋时间），ChatGPT 和 API 的请求失败率峰值达到 75%，付费和免费用户一起遭殃。原因不是攻击，也不是流量洪峰，是例行维护：给全栈做认证的 Primary API 服务所用的 Postgres 数据库，两台只读副本在维护中同时挂了。副本是承重的，主库没事也没用，依赖它的请求路径全倒了。

模型没坏，底下的层先坏了。Prompt 被偷那件事也一样：模型没坏，链条上的人和配置先坏了。

我们这一年把 Agent 越推越深：让它写代码、让它提交、让它调 API、让它管仓库。能力是上去了，但每一层新能力都在给攻击面加一层新入口。这周的两件事合起来就是一句话：**Agent 时代的安全账，不能只算模型那一层。**
